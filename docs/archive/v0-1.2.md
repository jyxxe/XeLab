# 通用插件化平台架构设计文档

**文档版本：** 1.2  
**架构类型：** 微内核 + 独立容器插件 + 能力驱动  
**主要技术栈：** Rust / C++  
**运行方式：** 单节点 Linux 主机 + 独立 CPU 容器  
**内核资源预留：** 至少 4 vCPU / 16 GiB 内存  
**WebUI：** 独立插件，通过内核管理 API 提供交互界面  
**插件开发者：** 内部及第三方开发者  
**GPU 支持：** 暂不支持

---

## 1. 项目目标

构建一个通用的、完全插件化的平台。平台不局限于 Web 应用，可以承载 AI 服务、自动化任务、数据处理、业务服务、工具集成和其他可扩展能力。

平台提供统一的插件开发规范、安装管理、依赖解析、运行时调度、资源隔离、API 转发和任务编排能力。

当前方案以单节点部署为实际运行前提。平台内核、必要的基础设施和插件容器运行在同一台 Linux 主机上；多节点仅保留接口扩展空间，不属于当前交付范围。

第三方开发者可以按照平台规范开发插件。只要插件满足相应的接口契约、安全要求和资源约束，就可以在不修改平台核心代码的情况下安装和运行。

### 1.1 核心目标

1. 插件独立开发、打包、安装、启用、升级和卸载。
2. 插件运行于独立容器，不直接加载到平台核心进程。
3. 支持 Rust、C++ 等不同技术栈的插件。
4. 插件之间通过统一的能力契约进行依赖和调用。
5. 平台通过 API 兼容层统一接收请求并转发至已启用的插件。
6. 支持 AI 服务、自动化任务、数据服务、WebUI 和组合型插件。
7. 为每个插件提供独立的 CPU、内存、临时存储和持久化数据盘。
8. 支持插件故障隔离、任务恢复、权限控制和运行审计。
9. 支持单节点上的第三方插件生态，为未来多节点研究保留模块接口。
10. 内核至少预留 4 vCPU 和 16 GiB 内存，插件资源从扣除内核及宿主基础设施预留后的容量中分配。
11. WebUI 可以独立安装、禁用、升级和替换；内核通过管理 API 与本机 CLI 提供不依赖 WebUI 的管理和恢复能力。
12. 支持包含 Guest 的用户角色、可复用权限组，以及按父级权限边界创建子账户和 API Key 的分层授权体系。

### 1.2 核心设计原则

- **微内核原则：** 核心只负责稳定的公共能力，不直接实现具体业务插件。
- **独立运行原则：** 插件是独立的部署和生命周期管理单位。
- **能力驱动原则：** 插件通过声明和提供标准能力参与系统。
- **契约优先原则：** 插件间依赖公开、版本化的接口，而不是内部实现。
- **资源隔离原则：** CPU、内存、存储和网络访问均由平台统一治理。
- **失败隔离原则：** 单个插件故障不应导致平台整体不可用。
- **安全默认原则：** 第三方插件默认不可信，必须显式授权。
- **状态持久化原则：** 插件数据和长期任务状态不能只保存在容器内存中。
- **内核资源预留原则：** 插件不得占用内核预留资源，资源不足时应等待或拒绝启动插件。
- **界面插件化原则：** WebUI 负责展示与交互，内核保留管理 API、认证授权和生命周期控制。

## 2. 总体架构

平台划分为控制面、运行面、能力与通信层、任务编排层、存储层和插件生态层。

### 2.1 架构组成

#### A. 平台控制面

负责管理整个插件生态。

主要模块：

- 插件注册中心
- 插件安装与版本管理
- 依赖解析器
- 生命周期管理器
- 资源管理器
- 容器调度器
- 权限与安全策略中心
- 配置管理器
- 版本化管理 API 与本机 CLI

控制面决定插件能否安装、启用、升级和运行，但不直接执行插件的业务逻辑。

#### B. 插件运行面

负责实际运行插件。

主要模块：

- 容器运行时管理器
- 插件进程监督器
- 健康检查
- CPU 和内存限制
- 数据卷管理
- 网络访问控制
- 故障检测与恢复

每个插件运行在独立容器中。插件之间不能直接访问彼此的进程、文件系统或内部端口。

#### C. 能力与通信层

负责插件之间以及外部调用方与插件之间的通信。

主要模块：

- 能力注册中心
- 服务发现
- API 兼容层
- 请求路由
- RPC 通信
- 事件总线
- 协议转换
- 调用授权与限流

#### D. 任务编排层

负责自动化任务和跨插件工作流。

主要模块：

- 触发器管理
- 定时调度
- 任务队列
- 工作流执行
- 依赖步骤控制
- 重试与超时
- 任务状态持久化
- 任务恢复与取消

#### E. 存储层

负责平台元数据、插件数据和任务状态。

主要模块：

- 平台元数据库
- 插件持久化数据卷
- 临时存储
- 插件制品仓库
- 任务状态存储
- 日志与审计存储

#### F. 插件生态层

面向插件开发者和管理员。

主要能力：

- 插件 SDK
- 插件打包规范
- 插件清单规范
- 契约测试工具
- 插件仓库
- 插件签名与完整性校验
- 插件发布与审核
- 版本兼容性管理

### 2.2 架构关系

外部客户端通过 API 兼容层访问平台能力。

API 兼容层查询能力注册中心，选择符合请求要求且已经启用、健康和获得授权的插件实例。

插件管理器负责安装、启用和停止插件；依赖解析器决定插件依赖是否满足；资源调度器负责本机资源准入和实例资源分配；任务编排引擎负责长期任务和跨插件流程。

这些模块职责独立，通过明确的内部接口协作。

### 2.3 内核与 WebUI 的边界

内核负责生命周期、权限、能力注册、受控路由、资源调度、任务控制和管理 API。内核的启动、运行和恢复不能强依赖 WebUI 插件。

WebUI 以独立插件运行，提供插件管理、资源查看、配置编辑和任务监控等交互界面。所有管理动作调用内核的公开管理 API，由内核执行授权检查和实际操作。

本机 CLI 直接访问内核管理接口，使用独立于 WebUI 的认证方式。WebUI 未安装、被禁用或升级失败时，管理员仍能检查状态、调整配置并恢复 WebUI。

## 3. 核心领域模型

平台必须区分插件、能力、服务实例、依赖和任务。

### 3.1 Plugin：插件

插件是安装、部署、升级和卸载的基本单位。

一个插件可以提供多个能力，也可以依赖其他插件提供的能力。

插件具有唯一标识、版本、制品来源、运行配置、权限声明和资源要求。

### 3.2 Capability：能力

能力是平台对外暴露和进行组合的基本单位。

例如：

- `ai.text-generation`
- `ai.embedding`
- `ai.reranking`
- `document.parse`
- `web.search`
- `storage.object`
- `automation.execute`

能力具有明确的接口契约、版本、输入输出格式、错误语义和运行要求。

一个能力可以有多个插件实现。平台可以依据权限、兼容性、可用性和调度策略选择合适的实现。

### 3.3 Service Instance：服务实例

服务实例是某个插件实际运行并提供服务的实例。

一个插件可以只运行一个实例，也可以根据负载、隔离和扩展策略运行多个实例。

实例具有独立的运行状态、容器标识、资源分配、通信地址和健康状态。

### 3.4 Dependency：依赖

依赖描述插件或任务需要什么能力、接口版本及运行条件。

依赖分为：

- 强依赖：缺失时无法正常提供服务。
- 可选依赖：缺失时允许部分功能不可用。
- 能力依赖：只要求存在满足契约的提供者。
- 实现依赖：明确要求特定插件或实现。

平台优先鼓励能力依赖，避免业务插件与具体实现形成不必要的强耦合。

### 3.5 Task：任务

任务是一次可以被调度、执行、追踪和恢复的工作实例。

任务可以调用一个或多个插件能力，并根据步骤之间的依赖关系执行。

任务状态、执行进度和必要的恢复信息由平台持久化管理。

### 3.6 身份与授权对象

用户账户、服务账户、插件实例身份、WebUI 客户端和 API Key 必须区分。角色与权限组描述动作及资源范围，子账户与派生凭证通过可追溯的授权链继承权限。具体规则见第 13.6 至 13.13 节。

## 4. 插件类型

插件基础管理模型保持统一，但不同插件可以声明不同的能力类型和运行特征。

### 4.1 AI 服务插件

提供模型推理及相关 AI 能力。

包括文本生成、Embedding、重排序、图像处理、音频处理和其他推理服务。

AI 插件需要明确支持的能力、请求格式、流式输出、超时、取消、上下文限制及资源要求。

平台不假设所有 AI 插件都支持相同的能力。

### 4.2 自动化插件

提供触发器、任务动作和可执行工作流节点。

自动化插件负责定义任务逻辑，但通用的任务调度、状态持久化、重试和恢复由平台负责。

### 4.3 数据服务插件

提供数据查询、数据写入、文件处理、搜索和外部系统适配能力。

数据访问必须经过明确授权，不允许插件直接读取其他插件的内部数据目录。

### 4.4 工具插件

提供可供其他插件或任务调用的原子操作。

例如网页搜索、文件生成、外部 API 调用、文档转换等。

### 4.5 组合型插件

组合多个已有能力，提供更高级的服务。

例如 AI 研究助手可以组合文本生成、网页搜索、文档解析和文件输出能力。

组合型插件不必重新实现底层服务，但必须明确声明依赖、失败策略和资源需求。

### 4.6 基础设施插件

提供缓存、存储、消息传递或其他公共服务。

此类插件可以向其他插件提供能力，但平台自身的关键控制能力不应依赖某个可随意卸载的第三方插件。

### 4.7 WebUI 插件

WebUI 是提供浏览器界面的插件，可以作为官方默认安装项，也可以由其他兼容实现替换。默认安装不代表自动获得管理权限。

WebUI 可以提供静态前端和必要的界面后端，使用独立容器、版本、健康检查和资源配额，其 CPU、内存及存储计入插件资源池。

WebUI 必须遵守以下边界：

- 插件安装、启停、授权和资源修改由内核管理 API 执行，WebUI 只提交请求和展示结果。
- 管理请求携带可验证的用户身份；如经过 WebUI 后端代理，内核仍需校验用户权限与插件代理权限，不能默认授予 WebUI 全局管理员凭证。
- WebUI 不直接读写平台元数据库，不挂载容器运行时管理接口或宿主敏感目录。
- 内核启动不等待 WebUI 就绪；WebUI 不应将所有业务插件健康作为自身启动条件，业务插件不可用时应展示状态或降级。
- WebUI 独立禁用、升级或退出时，内核管理 API、本机 CLI 和其他插件继续提供各自的服务。
- WebUI 可以作为平台默认页面，但默认入口及路由变更由内核管理，不能覆盖内核管理接口。

## 5. 插件清单与契约管理

每个插件必须包含标准化的插件清单。

清单至少描述：

- 插件唯一 ID 和显示名称。
- 插件版本与发布者。
- 支持的宿主 API 版本。
- 插件入口和运行环境要求。
- 支持的操作系统与 CPU 架构。
- 提供的能力及其接口版本。
- 依赖的能力和插件。
- 必需及可选权限。
- CPU、内存、数据盘和临时存储需求。
- 健康检查和生命周期行为。
- 配置项及其验证规则。
- 数据迁移与兼容性要求。
- 对于 WebUI 插件，声明界面入口、路由前缀、前端基础路径及管理 API 版本约束。

插件清单是平台审核和调度的输入，而不是插件获得权限或资源的凭证。

实际权限和资源配额必须经过平台策略审核。

### 5.1 契约版本管理

能力契约应独立于具体插件版本进行管理。

当接口发生不兼容变化时，应发布新的契约主版本或独立能力版本。

平台在安装和启动时验证兼容性，避免插件成功安装却无法被正确调用。

对于 API 兼容层，还需要区分外部协议版本、平台内部能力契约版本和插件自身版本。

## 6. API 兼容层

API 兼容层是外部请求进入插件生态的统一入口。

它不仅是普通的反向代理，还承担协议兼容、路由匹配、授权检查、请求转换和响应标准化。

### 6.1 核心职责

1. 接收 HTTP、SSE 或其他受支持的外部请求。
2. 验证调用者身份、租户和访问权限。
3. 匹配平台内置 API、插件声明式路由或能力调用路由。
4. 根据能力、模型别名或路由规则确定目标插件。
5. 检查目标插件是否已启用、健康且满足依赖条件。
6. 将请求转换为插件支持的内部契约。
7. 通过受控通信通道转发请求。
8. 处理响应、错误、流式数据和取消信号。
9. 记录调用日志、耗时、错误及必要的审计信息。

### 6.2 支持的路由模式

**标准兼容路由**

对外提供统一协议，例如 OpenAI 兼容 API，使不同的模型插件能够通过相同的外部接口访问。

**插件声明式路由**

插件声明需要开放的路径、方法和请求响应契约，由平台审核和注册。

**能力调用路由**

调用方指定目标能力，平台根据能力约束和调度策略选择实际提供者。

三种路由模式共享统一的认证、授权、限流和审计机制。

### 6.3 路由生命周期

插件安装不代表路由自动开放。

只有完成启动、健康检查、依赖验证和权限审核的实例，才能进入可用路由表。

插件禁用或异常时，平台应将其移出可用路由，并根据请求类型处理在途调用。

路由表可以使用内存快照提高性能，但权限校验不能仅依赖缓存状态。

### 6.4 故障与流式响应

API 兼容层必须支持调用超时、取消、连接断开、插件异常和服务不可用等情况。

流式 AI 响应应能正确传播取消信号，并避免在插件退出后继续保留无效连接。

自动切换备用插件之前，必须判断请求是否可以安全重试，不能对具有非幂等副作用的请求进行无条件重放。

### 6.5 WebUI 与管理入口

WebUI 页面和静态资源通过平台网关转发到已启用的 WebUI 插件，使用独立的路由命名空间，例如 `/ui/{plugin_id}/`。平台根路径可以指向管理员选定的默认 WebUI。

路径前缀仅用于路由，不构成浏览器安全隔离边界。互不信任的 WebUI 应采用独立源或受控沙箱，隔离会话与浏览器存储；参见 [浏览器同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)。

内核管理 API 使用平台保留的命名空间，例如 `/api/platform/v1/`。插件不能注册或覆盖该命名空间；浏览器和 WebUI 后端发起的管理调用均由内核验证身份、权限并记录审计。

浏览器管理令牌的用户、UI 客户端标识及授权范围由内核签发和验证。跨源调用仅允许经批准的来源，使用 Cookie 会话的管理接口还需防止跨站请求伪造。

网关应区分页面及静态资源转发与能力 RPC，不能要求所有 WebUI 内容都转换为 Protobuf。界面使用的 API 版本需要参与兼容性校验。

WebUI 不可用时，网关返回明确的界面不可用响应，内核管理 API 和本机 CLI 保持独立可用。首次初始化、身份恢复及 WebUI 的安装和回滚均须存在不依赖 WebUI 的受控管理路径。

## 7. 能力注册与服务发现

能力注册中心维护能力提供者与实际运行实例之间的映射关系。

每个可用实例应记录：

- 插件 ID 和版本。
- 能力名称与契约版本。
- 实例标识与通信地址。
- 启用状态与健康状态。
- 支持的功能特性。
- 权限与资源约束。
- 可选的优先级和调度标签。

能力注册中心不负责启动或停止插件，它只管理可供调用的能力与实例信息。

### 7.1 能力选择策略

当一个能力有多个提供者时，平台先过滤不符合权限、契约、健康状态和运行约束的候选者，再依据策略选择实例。

选择策略可以考虑：

- 调用方指定的实现或模型别名。
- 能力契约与功能特性。
- 租户授权和数据区域。
- 实例健康状态。
- 负载与并发限制。
- 调用成本和延迟目标。
- 备用提供者策略。

对于有状态操作或长时间任务，切换提供者之前必须明确任务恢复和数据一致性语义。

## 8. 插件依赖解析

依赖解析器负责判断插件能否运行，以及需要建立哪些依赖绑定。

### 8.1 依赖解析流程

1. 读取插件清单及其依赖约束。
2. 查找已安装插件和可用能力提供者。
3. 检查接口版本、插件版本和兼容性。
4. 检查依赖冲突、缺失依赖及循环依赖。
5. 生成安装和启动计划。
6. 计算需要新增的运行实例及资源需求。
7. 通过资源调度器安排实例。
8. 在启动后建立实际能力绑定。
9. 持续监控依赖状态，并在异常时执行策略。

### 8.2 循环依赖

第一版应禁止无法安全初始化的强依赖循环。

需要相互协作的插件应优先通过事件、延迟绑定或独立工作流建立协作关系。

### 8.3 共享依赖

多个插件可以共享一个能力提供者。

平台应区分能力消费者数量与实际运行实例数量，避免因为每增加一个消费者就重复启动共享服务。

### 8.4 依赖失效

依赖不可用时，根据依赖类型和业务策略决定：

- 暂停相关任务。
- 将插件标记为受限状态。
- 重试或等待依赖恢复。
- 切换到兼容的备用提供者。
- 取消无法继续执行的任务。

依赖失效不应自动导致整个平台停止运行。

## 9. 插件容器与资源管理

所有第三方插件默认运行在独立 CPU 容器中。

平台统一管理容器的创建、启动、停止、重启和销毁。插件不能自行创建不受平台控制的容器。

GPU 暂不纳入资源模型。

### 9.1 CPU 配额

CPU 使用量由平台统一限制。

应支持以 vCPU 配额表达资源上限，例如 0.5、1、2 或 4 vCPU。

CPU 配额表示可用的计算时间预算，不必然意味着独占物理 CPU 核心。

只有在特定性能隔离需求下，才考虑 CPU 核心绑定。

### 9.2 内存限制

每个插件实例设置明确的内存上限。

超出限制时，容器可能被操作系统终止。平台应记录 OOM 事件，并根据重启策略进行恢复。

内存资源承诺应谨慎管理，不能仅依据所有插件的平均使用量进行超额分配。

### 9.3 存储资源

每个插件可以使用两类存储：

- 持久化数据盘：保存插件业务数据、索引和需要保留的本地文件。
- 临时存储：保存缓存、中间结果和可重新生成的数据。

插件程序文件应尽量只读，业务数据写入专属数据卷。

数据卷容量必须由实际支持配额的底层存储机制实施，不能仅依赖插件清单中的声明。

### 9.4 资源需求与实际配额

平台应区分：

- 最低运行需求。
- 开发者推荐配置。
- 管理员批准的资源上限。
- 调度器实际分配的资源。

插件不能自行决定最终资源配额。

### 9.5 资源不足

资源调度器应维护本机扣除内核及宿主基础设施预留后的可分配 CPU、内存、持久化存储和临时存储容量。

资源不足时，插件应进入等待资源状态或返回明确的调度失败，而不是无限制地启动实例。

### 9.6 资源异常

CPU 长期满载、内存超限、数据盘写满和实例崩溃都需要有明确的监控与处理策略。

平台应支持配额审计、资源统计、告警、有限重启和故障隔离。

### 9.7 内核预留与单节点资源预算

内核资源池的最低预留为 **4 vCPU 和 16 GiB 内存（4C16G）**。管理员可以提高预留，当前部署策略不允许将其调低。这是为内核保留的容量下限，不是内核的实测常驻用量，也不是将内核硬限制在该用量以内。

资源预算分为三部分，必须明确各常驻服务的归属，避免漏算或重复计算：

| 资源区域 | 包含内容 | 分配规则 |
|---|---|---|
| 内核预留 | 控制面、核心网关、能力注册、调度与任务控制、管理 API 等核心服务 | 至少 4 vCPU / 16 GiB，插件不可借用 |
| 宿主及基础设施预留 | 操作系统、容器运行时、独立部署的元数据库、队列及日志服务等 | 根据实际部署另行配置，不挤占内核最低预留 |
| 插件资源池 | WebUI、AI、自动化、数据服务及其他插件实例 | 仅使用扣除上述两类预留后的剩余容量 |

其中，平台关键元数据库等必要基础设施应由宿主或平台部署系统管理，不能依赖某个可任意禁用的业务插件来维持内核运行。

```text
plugin_cpu_pool = host_cpu - kernel_reserved_cpu - system_reserved_cpu
plugin_memory_pool = host_memory - kernel_reserved_memory - system_reserved_memory

kernel_reserved_cpu >= 4 vCPU
kernel_reserved_memory >= 16 GiB

sum(plugin_instance_cpu_limits) <= plugin_cpu_pool
sum(plugin_instance_memory_limits) <= plugin_memory_pool
```

本版按插件实例获批的 CPU、内存上限进行准入，不超售、不借用空闲的内核预留。WebUI、共享依赖实例和升级时并行运行的新旧实例均计入插件池；共享实例只计一次。

预留必须同时落实到调度账本与运行时限制：对插件资源池设置父级合计上限，对实例设置各自上限，并配置内核资源组的内存回收保护。仅设置单实例限额或 CPU 权重不能替代总量约束。内核超出预留的增长也需单独规划余量，预留不代表任意负载下的无条件可用性保证。

CPU 预留以 vCPU 计算时间预算表达，不表示独占四个物理核心。如需物理核心隔离，另行配置 CPU 绑定。具体资源控制语义以 [Linux cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html) 为准。

若宿主容量不足以满足内核和宿主基础设施预留，部署检查应失败。若满足预留但插件池不足，则保留内核管理能力，拒绝或延迟相关插件启动，并明确报告 WebUI 是否因资源不足无法启动。

因此，4C16G 不能作为整机可运行插件的最低配置；整机还必须容纳宿主基础设施及计划启用的全部插件。宿主新增的其他常驻负载必须纳入预算，未经预算的外部负载会破坏资源预留前提。

## 10. 数据卷与持久化

容器生命周期和插件数据生命周期必须分离。

容器重建、插件升级或进程重启，不应自动删除插件持久化数据。

### 10.1 数据卷规则

- 每个插件或实例只能访问明确授权的数据卷。
- 默认使用独立数据卷，避免插件之间直接共享可写目录。
- 容器重启后重新挂载原有数据卷。
- 升级时保留数据，并按需要执行版本化迁移。
- 禁用插件时保留数据。
- 卸载程序与删除数据是两个独立操作。
- 支持容量统计、备份、恢复和扩容。

### 10.2 多实例注意事项

同一个可写数据卷不能默认安全地挂载给多个并发实例。

如需横向扩容，应选择明确支持并发访问的存储方案，或者为不同实例分配独立数据卷。

平台应明确哪些数据属于实例级数据，哪些属于插件级共享数据。

### 10.3 平台元数据

平台元数据库负责保存插件清单、依赖关系、实例状态、资源分配、授权信息和任务元数据。

插件业务数据不应默认写入平台元数据库。

---

## 11. 自动化与工作流引擎

自动化插件提供触发器和任务动作，平台工作流引擎负责管理实际执行。

### 11.1 平台负责的能力

- 定时和事件触发。
- 任务创建与排队。
- 执行状态持久化。
- 依赖步骤控制。
- 超时和取消。
- 有限重试及退避策略。
- 检查点和任务恢复。
- 并发控制与资源配额。
- 执行历史和审计。

### 11.2 插件负责的能力

- 定义任务动作。
- 声明输入输出。
- 调用自身提供的服务。
- 按契约调用其他能力。
- 提供必要的进度和取消支持。
- 声明执行副作用和幂等要求。

### 11.3 长任务与恢复

任务执行状态应保存在平台管理的持久化存储中，而不是只保存在插件进程的内存中。

容器重启后，平台能够判断任务是否已经完成、是否需要重试，以及是否存在未完成的步骤。

平台不能假设所有任务都可以安全地重复执行。涉及扣款、发送消息或创建资源的操作，必须考虑幂等键、去重和补偿机制。

## 12. 插件通信协议

插件运行于独立容器，因此跨插件调用必须通过明确的进程间通信协议。

### 12.1 同步调用

建议使用 gRPC 和 Protobuf 作为内部服务调用与契约定义的基础。

适合查询、计算、AI 推理和需要明确返回结果的操作。

通信应支持超时、取消、身份认证、调用 ID、错误标准化和必要的流式响应。

### 12.2 异步事件

通过事件总线或消息队列处理异步通知、后台任务和跨插件事件。

需要定义事件版本、投递语义、重试、去重和失败处理规则。

### 12.3 通信边界

- 插件不得直接管理其他插件的进程。
- 插件不得私下依赖其他插件的内部网络地址。
- 外部请求必须经过平台的认证、授权和路由机制。
- 插件间调用必须具有可审计的调用身份。
- 不允许第三方插件绕过平台直接开放未经授权的公网端口。

## 13. 安全与权限模型

第三方原生二进制插件默认不可信。

独立容器只能提供一部分隔离能力，还需要结合操作系统安全机制、网络控制和最小权限原则。

### 13.1 容器安全

建议采用：

- 非 root 用户运行。
- 只读根文件系统。
- 最小化 Linux capabilities。
- seccomp 和适当的命名空间隔离。
- cgroups 资源限制。
- 禁止访问宿主敏感目录。
- 禁止访问容器运行时管理接口。
- 限制进程数、网络连接和临时磁盘使用。

对于高风险第三方插件，可以进一步评估更强的容器或微虚拟机隔离方案。

### 13.2 API 权限

插件必须显式声明所需能力。

平台负责审批并在每次敏感调用时检查权限。插件不能通过修改自己的清单来获取额外授权。

所有受保护的管理接口、能力调用和对象操作都必须经过内核授权。角色、权限组、父子账户与 API Key 的判断规则共用同一授权模块，WebUI 只负责展示和提交请求。

### 13.3 网络权限

默认禁止不必要的网络出口。

对于需要调用外部 API 的插件，应按策略控制目标地址、协议、端口、连接数和带宽。

### 13.4 凭证管理

API 密钥和其他敏感凭证由平台安全管理。

插件只应获取完成工作所需的最小权限凭证，不应直接访问平台的全部密钥或其他插件的凭证。

### 13.5 制品供应链

插件安装前应验证来源、签名和完整性，并进行适当的安全扫描和兼容性测试。

签名证明制品来源和完整性，但不能证明代码绝对安全。

### 13.6 身份与角色

用户账户代表具有独立身份的人或子账户；服务账户用于经批准的后台执行；插件实例身份标识实际执行容器；WebUI 客户端标识界面应用；API Key 是绑定账户及授权链的调用凭证，不是新的用户账户。

首版内置以下角色模板，角色名称不是独立的授权依据，实际操作还需检查资源范围、继承上限和凭证条件：

| 角色 | 默认职责 |
|---|---|
| Owner | 用户与授权管理、插件准入、系统配置和恢复管理 |
| Operator | 查看运行状态、启停插件、升级已批准版本和故障处置 |
| Member | 调用明确获授权的能力，管理自身任务和业务资源 |
| Auditor | 查看脱敏审计记录及获准查看的运行信息 |
| Guest | 访问明确开放的页面、能力及本人自助账户接口，默认无平台运维、其他用户数据及凭证的访问权 |

所有已认证且启用的用户，包括 Guest，均可在平台配额内创建自己的子账户和 API Key；这类自助操作与管理其他用户的权限分开，例如 `account.child.create`、`credential.api-key.create`。Guest 的派生对象仍受该账户当前授权约束，不会仅因创建行为获得额外权限。

如开放匿名访问，应使用单独的 Anonymous 身份，仅允许明确标记的公开访问。Anonymous 没有用户账户，因此不能直接创建子账户或 API Key；注册后按实际授予的角色处理。

### 13.7 权限组

权限组是可复用的权限规则集合，不是用户成员分组。每条规则包含动作、目标资源或范围，以及必要的条件。例如：

```text
group: document-reader
  capability.invoke  -> capability/document.parse
  task.read          -> 授权范围内的任务
  volume.read        -> volume/reports

group: plugin-operator
  plugin.read        -> plugin/document-parser
  plugin.enable      -> plugin/document-parser
```

角色组织默认职责，权限组提供细粒度授权。一个用户可以绑定多个权限组，其允许规则在各自有效的授权来源内取并集，再受系统规则与继承上限约束；移除某一组只撤销该来源，不能误删其他独立有效的授权。

用户可以把自身当前权限的部分或全部整理成个人权限组，用于创建子账户或 API Key。公共权限组的发布和对其他账户的绑定需要相应管理权限。创建、修改或绑定权限组不能自动赋予创建者原本没有的权限。

首版权限组保持扁平，不支持组嵌套。组定义需要版本化，派生授权默认绑定选定版本及展开后的权限上限；发布新组版本不会静默扩大已有子账户或密钥的权限，扩权需重新授权。

插件声明的权限必须位于自身命名空间；插件清单和权限组均不能修改内核保留的管理权限定义。

### 13.8 子账户与权限继承

子账户具有独立 ID、登录凭证、会话、状态和审计记录，并通过不可由其自行修改的 `parent_id` 关联父账户。子账户不共享父账户密码，也不因身份继承自动共享业务数据。

创建时提供以下继承方式，均保留父级授权链：

| 继承方式 | 权限上限 | 父账户后续变化 |
|---|---|---|
| 部分继承 `selected` | 创建者选定的动作、资源范围或权限组版本展开结果 | 父级撤权立即收窄；父级扩权不自动扩大该上限 |
| 全部继承 `all_snapshot` | 创建时父账户全部有效权限的快照 | 父级撤权立即收窄；新增权限需重新授权 |
| 持续全量继承 `follow_parent` | 显式选择实时跟随父账户的当前有效权限 | 父级增减授权均同步影响下级 |

默认使用快照方式；持续全量继承应明确展示其会同步获得父级未来新增权限的语义。两种“全部”方式都仍受资源范围、账户状态、凭证条件和系统策略约束。

子账户可以继续创建子账户，形成单父级、无环的账户树。平台配置最大深度、每账户子账户数及账户树总量，禁止通过增加层级绕过限制。

父账户可以在自身授权范围内调整下级的权限上限，或暂停、禁用下级。子账户只能按获准规则进一步收窄自身授权，不能通过修改角色、权限组或调用账户管理接口抬高上限、脱离父级或创建不受继承约束的根账户。

继承必须保留原始资源边界。`own` 等相对范围在授权时绑定明确主体和判断规则，不能通过复制角色或替换账户 ID 扩大范围。父子关系本身不自动赋予彼此业务数据的读取权，数据访问仍需匹配具体授权。

### 13.9 API Key

API Key 绑定所属账户，使用与子账户一致的部分、全部快照或持续全量继承方式。每个密钥具有独立的授权上限、状态、有效期和可选的目标服务、来源网络及调用额度约束。

创建密钥时只展示一次明文，服务端保存用于校验的安全摘要和可展示的标识前缀；日志与审计不保存完整密钥。密钥支持单独吊销和轮换，泄露或吊销一个密钥不应自动使该账户的其他独立密钥失效。

密钥用于调用获授权的 API，不直接充当浏览器登录会话。持有密钥不代表持有账户全部权限，尤其不能只根据所属账户的角色跳过密钥自身范围校验。

如果允许通过 API Key 或其他受限委托继续创建子账户或密钥，创建者有效权限按当前凭证实际可用的权限计算，并保留 `issuer_credential_id` 或等价的源委托链。派生对象的范围、有效期和调用条件不得突破源凭证边界，源凭证过期或吊销后，其派生链也失效，避免用短期窄权限密钥换取长期宽权限凭证。

用户通过正常交互登录创建独立凭证时，授权来源为用户账户，不要求该登录会话永久保持有效；登出单个会话与禁用用户账户分别处理。

### 13.10 授权计算与插件委托

每次请求先验证主体、凭证及授权链的状态，再按动作和实际目标资源计算授权。权限集合以下列形式表达，其中资源范围和条件也是权限的一部分：

```text
子账户有效权限 = 父账户当前有效权限 ∩ 子账户授权上限 ∩ 子账户本地收窄规则
API Key 有效权限 = 所属账户当前有效权限 ∩ 密钥授权上限 ∩ 密钥调用条件
通过凭证派生的对象有效权限 = 账户链计算结果 ∩ 源凭证链当前有效权限

用户委托插件执行的有效权限 = 当前调用主体有效权限
                        ∩ 插件获批的代理权限
                        ∩ 本次执行委托上限
                        ∩ 目标资源策略
```

持续全量继承的授权上限按父级当前权限计算，快照和部分继承按已批准的固定上限计算。所有祖先和源委托的有效性都参与判断，不能只校验直接父级或只信任令牌中缓存的角色名称。

例如父账户具有“文档读取、文档写入”，子账户只继承“文档读取”，该子账户创建的全部权限 API Key 仍只有“文档读取”。父账户失去读取权限后，该子账户和密钥也不能继续读取。父账户新增“文档删除”不会扩大快照授权，但会影响显式选择持续全量继承的下级。

用户委托和服务账户执行必须明确区分。交集规则用于被委托的业务操作，不要求用户取得服务内部模型文件或密钥的直接读取权；用户授权失败后，插件不得自动改用服务账户绕过拒绝。

内核记录发起用户、当前子账户、实际插件实例、使用的密钥 ID、委托链及目标资源。插件自报的身份请求头不能作为可信身份。主体与代理执行者的语义可参考 [OAuth Token Exchange](https://www.rfc-editor.org/rfc/rfc8693.html)，具体继承规则以本节平台策略为准。

### 13.11 撤权、任务与审计

父账户或任一祖先被禁用、到期时，其子账户及相关凭证链停止获得有效授权。删除账户采用保留授权链标识的归档规则，不能删除父记录后把子账户变成独立根账户。已吊销的密钥和委托不可通过重新启用父账户而复活，需要重新签发。

权限组解绑、父级收权及密钥范围调整后，新的受保护调用按更新后的授权判断。单节点可以维护本机权限版本及缓存失效通知，但敏感调用必须确认当前版本与吊销状态；不能仅等待旧令牌自然过期。默认拒绝及逐请求授权检查参考 [OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

定时任务保存账户主体、运行身份、资源范围、固定的执行委托上限和授权来源，不能保存用户会话作为长期授权。每次触发、出队、重试及后续步骤重新检查完整授权链。即使账户选择持续全量继承，已有任务也不会自动扩大自身固定的执行委托上限。

撤权后阻止新的执行与后续调用，并尝试取消在途操作；已经完成的外部副作用仍需按幂等、结果核实或补偿规则处理。

审计至少关联实际操作账户、父级授权链、源凭证、权限组及版本、目标资源、动作、授权结果、权限策略版本和任务 ID。父账户管理下级、组变更、密钥签发与吊销、根账户恢复均记录审计。

### 13.12 配额、初始化与恢复

账号、子账户和密钥共用账户树的资源边界。平台分别限制账户数量、层级、密钥数量、请求并发及业务调用额度，沿祖先链累计核算，不因创建新主体而获得新一份父级额度。创建和额度扣减须处理并发，避免同时创建绕过总量限制。

权限决定是否允许操作，配额决定允许消耗多少资源。上述主体不自动获得专属插件实例；确需按用户隔离实例时，所有新增实例仍计入插件池，不得挤占内核至少 4 vCPU / 16 GiB 的预留。

首次通过受保护的一次性本机引导建立独立 Owner，之后关闭初始化入口。平台至少保留一名有效的独立 Owner；派生账户的 Owner 权限仍受父级约束，不能计作独立恢复根。紧急恢复依赖受保护的宿主身份和内核 CLI，WebUI 不可用时仍能执行，并记录审计。

### 13.13 最小持久化模型

| 对象 | 主要字段或职责 |
|---|---|
| Account | ID、类型、父账户 ID、状态、有效期、权限版本 |
| Role / Permission | 角色模板、命名空间、动作及资源类型 |
| PermissionGroup / GroupVersion | 权限组所有者、版本及规则集合 |
| Grant / RoleBinding | 授权来源、主体、动作、资源范围及有效期 |
| InheritanceGrant | 父级、继承方式、固定上限或跟随规则、源凭证关联 |
| Credential / Session | 所属账户、校验摘要、授权上限、条件、状态及有效期 |
| ExecutionDelegation | 任务或调用的主体、代理执行者、固定委托上限及状态 |
| Quota / Usage | 账户树额度、资源使用与并发计数 |
| AuditEvent | 身份链、变更、授权结果、策略版本及关联请求 |

账户树与源凭证链必须能够完整追溯并检测循环。授权、撤销和配额变更由内核执行，WebUI 与其他插件不能直接修改这些表。

## 14. 插件生命周期

插件生命周期应由平台统一控制。

### 14.1 主要状态

- Discovered：已发现。
- Validated：已验证。
- Installed：已安装。
- Disabled：已禁用。
- Starting：启动中。
- Ready：健康检查通过，可以接受请求。
- Degraded：部分能力不可用。
- Failed：运行失败。
- Stopping：停止中。
- Uninstalling：卸载中。

已安装、已启用和正在运行是不同概念，不应合并为单一状态。

### 14.2 启用流程

1. 验证插件清单和制品。
2. 检查依赖与接口兼容性。
3. 审核权限和资源需求。
4. 检查本机插件池预算并分配资源，保留内核至少 4 vCPU / 16 GiB。
5. 创建容器并挂载数据卷。
6. 启动插件并建立通信。
7. 执行健康检查。
8. 注册服务和能力。
9. 将符合要求的路由开放给调用方。

### 14.3 禁用流程

1. 停止接受新请求。
2. 移除或冻结相关路由。
3. 排空或取消在途调用。
4. 按策略暂停或取消相关任务。
5. 停止插件并释放运行资源。
6. 保留插件数据和必要的审计记录。

### 14.4 升级与回滚

建议采用新版本并行启动、健康检查、切换流量、旧版本排空的方式。

单节点并行升级需要提前检查新旧实例同时运行的插件池容量，不得借用内核预留。容量不足时应等待资源，或采用明确安排的停止旧版后再启动新版的升级流程，并告知服务中断范围。

升级失败时应能回滚到已知可用版本。

如果涉及数据迁移，必须提前定义迁移顺序、兼容窗口和回滚策略。

## 15. 故障恢复与可观测性

平台需要统一监控插件运行状态、资源使用和调用质量。

### 15.1 故障类型

包括：

- 容器启动失败。
- 插件进程异常退出。
- 健康检查失败。
- CPU 或内存超限。
- 数据盘写满。
- 依赖服务失效。
- API 调用超时。
- 网络连接异常。
- 任务执行失败。

### 15.2 恢复策略

平台应支持有限重启、退避重试、故障隔离、备用提供者切换和任务恢复。

连续失败的实例应进入故障状态，避免无限重启和资源浪费。

单节点恢复以宿主仍可用、持久化数据完整为前提。内核重新启动后应对账元数据、已有容器、资源占用和路由，再恢复符合条件的实例；WebUI 恢复不应阻塞内核管理接口就绪。

### 15.3 可观测性

至少记录：

- 插件启动、停止和升级事件。
- 资源使用与配额。
- API 调用量、延迟和错误率。
- 依赖解析与绑定结果。
- 任务执行历史。
- 权限拒绝和安全事件。
- 容器异常、OOM 和重启原因。

日志应包含插件 ID、实例 ID、调用 ID 和任务 ID 等关联字段，并避免记录敏感凭证或不必要的个人数据。

## 16. 推荐技术选型

| 层次 | 推荐方向 | 主要职责 |
|---|---|---|
| 平台控制面 | Rust | 生命周期、依赖、权限和调度控制 |
| 插件实现 | Rust / C++ | AI 服务、业务逻辑和数据处理 |
| 内部通信 | gRPC + Protobuf | 跨语言服务契约 |
| 容器管理 | containerd 等 OCI 兼容运行时 | 容器生命周期 |
| 资源限制 | Linux cgroups v2 | CPU、内存和进程资源治理 |
| 容器隔离 | Linux namespaces、seccomp 等 | 文件、进程和系统调用隔离 |
| 元数据存储 | PostgreSQL 或同类关系数据库 | 插件、依赖、实例和任务元数据 |
| 事件与任务队列 | 消息队列或持久化任务队列 | 异步任务和事件投递 |
| 插件制品仓库 | OCI 兼容或专用制品仓库 | 插件包、版本和签名 |
| 可观测性 | 结构化日志、指标、分布式追踪 | 监控和故障定位 |
| WebUI | 独立容器中的前端及可选界面后端 | 通过版本化管理 API 展示和操作平台 |

当前采用单节点部署，将本机资源准入、容器管理和能力注册设计成独立模块；多节点仅保留未来扩展接口，不引入当前不需要的分布式调度和一致性组件。

部署时先为内核预留至少 4 vCPU / 16 GiB，再核算宿主基础设施及插件预算。WebUI 按插件契约和管理 API 接入，其框架与发布周期独立于内核。

GPU 不纳入当前资源调度范围。

## 17. 部署与扩展策略

### 17.1 当前部署：单节点

在单台 Linux 主机上运行平台控制面和多个插件容器。

资源调度范围为本机，主要职责是预留扣减、插件准入、实例限额和资源回收。内核、宿主基础设施和插件池分别核算，WebUI 作为插件部署。

内核和必要基础设施由宿主服务管理机制启动，随后按依赖和预算恢复插件。WebUI 是可选管理界面，不参与内核启动的必要依赖链。

需要特别注意控制面与插件容器的权限隔离，并通过本机 CLI 提供不依赖 WebUI 的初始化和恢复入口。

### 17.2 单节点故障边界与备份

插件进程和容器故障可以在本机进行隔离和恢复，但同机多实例不能提供宿主级高可用。宿主宕机期间，内核、WebUI 和插件均可能不可用，当前方案不承诺跨节点故障转移。

平台元数据、任务状态和插件数据卷应持久化，并制定一致的备份与恢复流程。重要备份需要保存在宿主之外，避免本机磁盘损坏时同时丢失原始数据和备份。

宿主恢复后先恢复内核和必要基础设施，再对账并恢复插件。存在外部副作用的任务仍按其幂等与结果核实规则处理，不能因宿主重启而无条件重放。

### 17.3 后续扩展与插件生态

后续可以建设插件审核、签名发布、兼容性验证、灰度升级、资源计量和安全事件响应体系。

如未来确需多节点，需要另行设计控制面可用性、节点代理、数据卷位置与迁移、网络和任务执行归属。当前仅保留模块接口，不能假设单节点持久化已解决这些问题；扩展时应尽量保持插件基本契约稳定。

## 18. 关键验收标准

平台上线前至少应满足以下要求。

### 插件管理

- 新增合规插件不需要修改平台核心代码。
- 插件能够独立启用、禁用、升级和卸载。
- 依赖缺失、版本冲突和循环依赖能够被明确识别。
- 插件升级失败能够恢复到已知可用版本。
- WebUI 能够独立启用、禁用和升级；WebUI 停止后，可通过本机 CLI 检查并恢复插件。

### API 兼容层

- 只向符合条件的已启用插件路由请求。
- 能够正确处理插件不可用、超时和异常退出。
- 支持统一的身份认证、授权、限流和审计。
- 支持必要的流式响应和取消行为。
- WebUI 路由不能覆盖内核管理 API，WebUI 故障不会阻塞独立管理接口。

### 资源与存储

- CPU 和内存限制实际生效。
- 数据卷容量得到实际控制。
- 容器重启不会自动删除持久化数据。
- 插件无法访问未经授权的其他插件数据。
- 资源不足时能够拒绝或延迟启动。
- 内核至少 4 vCPU / 16 GiB 的预留被实际扣除，插件池合计上限与实例限额同时生效。
- WebUI 和并行升级实例计入插件池，预算不足时不得借用内核预留。
- 插件达到 CPU、内存配额时，内核仍能通过管理 API 或本机 CLI 完成状态查询、禁用和故障处置。

### 自动化任务

- 任务状态在平台重启后仍然存在。
- 长任务可以被监控、取消和恢复。
- 重试不会无条件重复执行非幂等操作。
- 依赖失效时，任务能够按策略暂停、重试或降级。

### 安全

- 第三方插件以非特权方式运行。
- 插件不能自行扩大权限。
- 插件无法直接访问宿主敏感资源。
- 网络访问和外部凭证受到控制。
- 插件运行和调用行为可被审计。
- WebUI 无法直接修改平台元数据库或访问容器运行时管理接口，管理操作按用户与插件身份授权。

### 用户、权限组与派生授权

- Guest 仅能访问获准的页面和能力，但与其他已认证用户一样可在配额内创建受限的子账户和 API Key。
- 多权限组可以组合，组修改、角色变更和新增绑定均不能突破父级或凭证授权上限。
- 部分继承、全部快照与持续全量继承具有明确且可验证的扩权和收权行为。
- 多层子账户和密钥始终受全部祖先及源委托约束，不能通过改组、换角色、创建根账户或再次签发凭证绕过限制。
- 祖先禁用、权限收回及密钥吊销能阻止后续调用、排队任务和后续步骤；单个独立密钥的吊销不影响其他独立密钥。
- 账户树的数量、层级和累计调用配额在并发创建与调用下实际生效。
- 子账户修改对象 ID 或复制角色不能扩大资源范围；父子关系不自动开放双方业务数据。

### 单节点恢复

- 宿主重启后能够恢复持久化元数据，并对账容器、资源占用和路由，避免重复创建实例。
- WebUI 未安装或不可用时，内核能够独立启动，管理员可以通过本机 CLI 初始化和恢复界面。
- 验证从宿主外备份恢复元数据与插件数据的流程，并明确单节点不提供宿主故障期间的连续可用性。

## 19. 分阶段实施计划

### 阶段一：单节点最小插件内核

实现插件清单、插件注册中心、最小能力注册与 RPC、生命周期管理、基本健康检查、内核管理 API 和本机 CLI，贯通单节点上的安装、容器启动与调用。

同步实现至少 4 vCPU / 16 GiB 的内核预留、本机插件池准入、插件池父级合计限制和实例 CPU、内存限制。基础隔离及授权随首个插件运行闭环落地。

用户权限同步实现内置角色（含 Guest）、版本化权限组、子账户树、API Key、继承上限、祖先与源凭证吊销检查，以及 CLI 管理和审计，避免在插件及 WebUI 接入后补建身份边界。

目标是让一个简单的 Rust 或 C++ 插件能够被独立安装、启动和调用，并在不依赖 WebUI 的情况下完成管理。

### 阶段二：容器与资源管理

完善插件池父级限制、数据卷容量控制、临时存储限制、容器监督、资源统计及故障恢复，并验证宿主重启后的状态对账。

目标是验证插件的资源边界、持久化数据保护及单节点重启恢复。

### 阶段三：API 兼容与 WebUI 插件

完善 API 兼容层、能力注册、请求转发、权限校验和响应转换，交付通过版本化管理 API 工作的官方 WebUI 插件。

WebUI 提供权限组管理、子账户创建与继承范围选择、密钥一次性展示和吊销入口；展示来源权限、实际有效权限及被父级限制的原因，持续全量继承须明确标识。

目标是让外部客户端可以通过稳定接口调用已启用的插件，同时验证 WebUI 独立升级、资源计入插件池及界面故障后的 CLI 恢复路径。

### 阶段四：依赖解析与跨插件调用

实现依赖图、版本约束、能力绑定、RPC 和事件通信。

目标是允许多个插件在不直接耦合内部实现的情况下相互协作。

### 阶段五：任务编排与 AI 能力

实现持久化任务、定时触发、工作流、长任务恢复和标准 AI 能力。

任务执行接入独立执行委托，验证父账户收权、禁用和源凭证吊销后暂停后续执行的规则。

目标是让自动化任务能够组合 AI 服务、搜索、数据处理和其他插件能力。

### 阶段六：第三方插件生态

实现 SDK、插件仓库、签名审核、契约测试、兼容性测试、灰度升级和安全审计。

目标是形成可以持续扩展的第三方插件生态。

## 20. 最终架构总结

本平台采用微内核架构，以独立容器作为插件运行边界，以能力契约作为插件协作边界，以 API 兼容层作为外部调用入口，以依赖解析器管理插件之间的关系，以任务编排引擎处理跨插件的长期执行。

当前运行边界为单节点 Linux 主机，内核至少预留 4 vCPU / 16 GiB，宿主基础设施另行预留，剩余资源构成插件池。WebUI 作为独立插件接入，内核通过管理 API 和本机 CLI 保持独立的管理与恢复能力。

平台负责：

- 插件的安装与生命周期。
- 插件依赖与能力绑定。
- API 请求的路由和协议兼容。
- CPU、内存和数据卷资源管理。
- 安全隔离、权限和审计。
- 任务调度、状态恢复和故障治理。
- 不依赖 WebUI 的管理接口与本机恢复入口。

插件负责：

- 实现声明的能力。
- 遵守统一接口和版本契约。
- 声明依赖、权限和资源需求。
- 在授权范围内执行任务。
- 提供必要的健康检查、取消和恢复支持。

最终目标是实现一个开放、可组合、可扩展的平台：新插件可以独立开发和部署，通过稳定的契约接入已有能力体系，并被其他插件或自动化工作流复用，而无需修改平台内核。

**核心原则：插件独立运行，能力统一注册，依赖统一解析，请求统一转发，资源统一治理，任务统一编排。**
