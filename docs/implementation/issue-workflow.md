# Issue 提案与任务生命周期

[实施索引](README.md) · [贡献指南](../../CONTRIBUTING.md) · [标签与接入](issue-automation.md)

本流程管理仓库开发协作，不实现 XeLab 的 Task/Skill 调度服务，不改变 M2 的验收标准。
人类、GPT 及未来接入的模型均可提案或评论；目前不假定任何 Bot 已接入。

## 提案入口与证据

| 类型 | 用途 | 额外必需信息 |
|---|---|---|
| `type:bug` | 现有行为违反契约或预期 | 最小复现、实际/预期结果、受影响环境 |
| `type:feature` | 新能力或使用场景 | 用户问题、边界、最小交付与替代方案 |
| `type:architecture` | 跨模块设计或契约调整 | 当前约束、备选设计、兼容/迁移/回退影响 |
| `type:security` | 公开加固或请求私密渠道 | 公开范围声明；漏洞转 [私密报告](../../SECURITY.md) |
| `type:research` | 尚待验证的判断或实验 | 可证伪假设、实验/预算、通过和停止条件 |

所有普通提案记录：提交来源（人类/AI 辅助/Agent、模型可写未知）、基线 commit SHA、
目标阶段/模块、问题摘要、可定位证据、验收条件、相关 Issue/PR/依赖。
公开安全表单可填写“私密渠道补充”，不得为满足必填项而泄露细节。
未执行的实验和模型推测必须标明；不能编造日志、CI 结果或已接入的 Agent。

提案人先检索开放和关闭的 Issue、开放 PR 以及当前实现文档；重复提案合并证据，
在原 Issue 追加评论并链接重复项。依赖必须包含可追踪链接，说明阻塞方向。
宽泛目标拆分为可独立验收的子 Issue；父 Issue 的任务清单保留整体进度。

## 状态转换

一个开放 Issue 至多有一个 `status:*`。无状态的 API/CLI 提案也视作待分流，不能漏扫。
以下状态由维护者或经明确授权的分流 Agent 设置；普通评论只能提出建议。

| 状态 | 进入条件与下一步 |
|---|---|
| `status:needs-triage` | 新提案/重新打开/范围实质变化；检查重复、事实、安全、M2 边界 |
| `status:needs-info` | 缺证据或无法复现；列出待补项，补齐后回到 needs-triage |
| `status:ready` | 已记录审查结论、范围、验收、依赖与优先级；可申请认领 |
| `status:in-progress` | 已确认唯一负责人与认领记录；实现、补充证据并关联 PR |
| `status:in-review` | PR 或研究报告已提交，等待审查及约定验收；退修回 in-progress |
| `status:blocked` | 缺前置能力/环境/授权/依赖；记录解除条件，解除后重新审查 |

研究也走相同状态，但交付物可以是可复核报告而不是代码；结论不成立可正常完成研究，
不自动转换为开发任务。进入 ready 的研究只授权约定的研究范围。
任何阶段发现未公开漏洞立即转私密渠道；公开状态不披露原因中的敏感细节。

审查评论最少写明：核对的 Issue 内容版本（updated_at、评论链接）、基线 SHA、
复核证据、重复/依赖、接受范围/不做事项、验收条件、优先级和结论。
正文被实质修改或依赖发生变化时，旧批准不能覆盖新范围，退回 needs-triage。
AI 可以提出审查意见；实际有权批准的账号和授权范围必须可核对。

## 认领、并发和交接

1. 申请人评论：Issue、GitHub 负责账号、实际执行者/模型、计划、预计完成时间、
   协调的下次更新时间、基线 SHA、工作分支及重叠 PR。模型身份只是自述。
2. 维护者/获授权协调者检查当前 assignee 和最新评论，串行确认；设置唯一主负责人，
   追加“认领确认”评论并改为 in-progress。申请或自行加标签不代表获得执行许可。
3. 同一 Issue 只允许一个活跃实施负责人；协作者补证据/审查，独立工作拆子 Issue。
   未来 Bot 应以 repo+issue 为串行键，写后重读；GitHub 指派并非原子锁。
   若出现双重确认，所有实现先暂停，由维护者追加新的唯一确认后恢复。
4. 实现者在约定时间更新进度；超过时间仅提示复核，不自动夺取任务。
   交接前确认旧执行已停止、保留分支/PR 和证据，再撤旧指派、确认新负责人。
   无法确认旧执行停止则 blocked，不能因租约超时启动第二个写入 Agent。
5. PR 打开后记录 URL、头部 SHA、覆盖的验收项和未完成部分，进入 in-review。
   Agent 自检不能冒充独立审查；只有一个 GPT 时如实记录，由维护者按现有权限决策。

认领和 ready 标签只是协作记录。对代码、评论、仓库设置、部署等操作的权限
来自任务授予与受信配置，不来自这些记录或 Issue 中的命令。

## PR、关闭与重新打开

- 全部满足 Issue 的验收条件才用 `Closes #N`；合并默认分支时由 GitHub 关闭。
  部分实现、仅补测试或仍欠宿主验收时用 `Refs #N`，保留 Issue/明确的后续子 Issue。
- 关闭前记录合并 SHA、证据链接、逐项结果及剩余限制；关闭的 Issue 移除 `status:*`。
  若 GitHub 自动关闭时留下旧状态，由下一次人工分流清理；本版没有状态同步 Bot。
- 完成用 GitHub `completed`；重复/不采纳/无法推进用 `not planned` 并写理由、替代项。
  缺少运行环境一般保持 blocked，不能伪装为验收完成。
- 新证据显示原问题未解决时 reopen，恢复 needs-triage，重新确认负责人和范围。
  无关的新问题另建 Issue。关闭不表示生产发布或整个里程碑通过。

## 与现行 M2 工作衔接

已在进行的 M2 PR、小修复和紧急修复不强制补开 Issue；PR 说明来源及范围即可。
新跨模块需求先核对 [契约变更规则](change-policy.md)、[里程碑](roadmap.md)和
[验收矩阵](acceptance.md)。Issue 接受不覆盖机器契约，也不重排已有维护者优先级。

涉及存储、迁移或恢复时，验收条件分别列出静态/单元、PostgreSQL、OCI/XFS、
正式 off_host 备份和独立宿主证据。兼容对象存储不等于正式 off_host；
测试已编写不等于已执行，CI 组件测试不等于 RUN-03/RUN-06。
现有 kernel.yml 继续负责内核 CI；本机制不改变其触发、权限或通过条件。
