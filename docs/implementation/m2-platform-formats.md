# M2 已验证格式卷的全平台备份与恢复

[实施目录](README.md) · [离线源](m2-offline-source.md) · [整体备份](m2-platform-backups.md) · [整体恢复](m2-platform-restores.md)

全平台离线捕获和目标恢复现接通已验证业务格式卷，继续支持原有 none 格式。
恢复保留逻辑卷 UUID 和既有格式事实，在新的物理根、文件系统和 project ID 上重建相同数据；
不通过修改格式标签完成转换，也不执行 Apply。公开非 none 制品安装门禁保持关闭。

## 源端要求

停机维护仍取得真实宿主/数据库租约，拒绝未完成的备份、恢复、格式任务、占用和卷清理。
每个未删除逻辑卷必须有完整 ready 分配、正确归属/规格/硬配额；反向也不允许没有逻辑卷
或逻辑卷已删除的 ready 分配。否则元数据库与物理归档的资源集合不一致，禁止发布备份。

none 卷必须保持 unversioned 且不携带其他格式绑定。非 none 卷必须为 verified，具有原
deployment、plugin、publisher、manifest digest、operation 和对象形式的历史证明。
源端核对原安装的不可变清单及运行配置支持范围，再核对真实 OCI 字节、原始清单摘要与元数据。
保留的旧格式卷按其原签名制品核对，不采用部署当前版本的格式来重新标记。

认证清单的每个版本化卷增加可选 format_binding，保存格式、上述逻辑身份和历史证明摘要。
无绑定的非 none 标签、绑定与格式不一致、缺失原制品或证明被改写都会拒绝。
已撤销发布者的历史数据仍可保存；捕获和恢复历史事实不会恢复发布者信任或迁移凭证。

## 目标端校验与发布

1. 使用认证回执和独立保管的主密钥读取清单，完整认证元数据库及每个对象。
2. 导入后对照清单重新核对格式绑定、原始清单、插件/发布者与证明摘要。
3. 在真实新 XFS 文件系统中预留完整容量，分配超过源高水位的新 project ID。
4. 解密、解包并再次检查真实磁盘字节、元数据和配额；重复执行仅重验已完成数据。
5. 在预留、最终物理复核及原子发布时重查格式绑定；任何变化保持恢复门禁关闭。
6. 只有全部内容及恢复 Owner 验证完成，才发布物理根/卷和 ready 门禁。

原格式证明保留为经过认证的历史事实，实际恢复读回证明保存在本次恢复检查点中。
逻辑卷身份相同、字节相同不会生成新的格式转换结论。部署仍禁用，旧凭证、Grant、发布者信任、
实例证书及挂载批准不恢复。当前恢复 Owner 必须重新登录、明确重信任所需发布者、批准部署，
才可通过正常控制器重新启用；旧会话或宿主权限不能代替这些操作。
资源归属不会转移；其他历史所有者仍须按[账户维护流程](m2-recovered-accounts.md)重新激活并取得明确新授权，不能借格式绑定接管其资源。

## 兼容性

当前内部元数据库仍为 14，不修改已发布 SQL 1–14、校验和或机器契约。
none 清单不输出新可选字段，旧清单缺少该字段时继续读取为无绑定。
非 none 清单必须使用支持本实现的可信二进制；旧二进制对未支持内容拒绝，不能用忽略字段绕过。
原生元数据库依旧要求精确迁移/列布局及相同 PostgreSQL 主版本，不执行输入 DDL。

## 测试与证据边界

PostgreSQL 回归覆盖孤立分配拒绝、标签不等于证明、格式/原制品绑定、历史证明篡改拒绝，
以及保持已撤销发布者状态；元数据 fixture 不代表真实初始化或 XFS。
现有整体恢复演练新增两个独立真实签名 OCI 程序初始化的格式 1 与格式 2 卷，同时保留原 none 卷、稀疏文件、链接、
实际源卷销毁、新数据库/内容库/文件系统、进程死亡续作及目标数据损坏拒绝。
恢复后分别通过当前 Owner 的实际登录、显式重新信任/批准、控制器和 Broker 检查两种格式的业务续写及原记录保留。
格式 2 源由空卷按正常初始化产生，不依赖格式 1 转换；格式变更的正式 AWS 验收仍独立记录。

新的特权执行必须以最终提交的 CI 结果为准，在完成前不计为通过。
组件使用独立测试数据库的合成容量和兼容对象存储，off_host 始终为 false。
这不代替正式 AWS、独立宿主恢复、生产 RUN-03 或完整不同格式升级/回退验收。
