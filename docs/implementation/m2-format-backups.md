# M2 格式迁移备份登记组件（开发中）

[实现索引](README.md) · [迁移 RPC](m2-migration-rpc.md) · [部署重建](m2-deployment-upgrades.md)

本组件为后续格式迁移保存、重新核对可用备份登记，尚未接入升级监督器。
格式不同的 upgradeDeployment / rollbackDeployment 仍拒绝；公开版本化制品安装入口
仍关闭。不能据此宣称完成格式迁移、不兼容数据回退或 RUN-06。

## 登记与实际对象

`upgrades::migration_backup::Registration` 要求同部署的备份处于 ready/off_host，
其原 backup 任务已经 succeeded，且仓库登记 ready。原任务的完整清单、安装、
部署配置、镜像摘要、主密钥引用、清单对象 UUID 和摘要必须彼此吻合。
升级应选择原格式安装的备份；不兼容回退应选择目标旧格式安装的备份。
安装元数据必须来自父任务当前可信安装检查，不能从客户端接受。

随后使用宿主正式 AWS 配置绑定原仓库，核对实际仓库身份标记和对象引用，读取
原加密清单并验证 AEAD、摘要、完整登记、卷选择及传输信息，再要求真实 off_host。
兼容对象存储始终保持 off_host=false；本地 MinIO 不能通过数据库字段变成正式备份。
一个 Ready 行或格式字符串本身均不能产生通过认证的备份点。

执行前须重新核对当前可用登记及原授权；再次使用对象时重新读取实际仓库/清单。
上层仍须持有部署围栏、原凭证和预算，并验证已冻结的私有克隆与备份完全一致，
或者把目标旧格式备份恢复至新的私有目录。最终格式证据来自实际业务 Verify。
本登记组件不停止运行时、不执行 Apply、不切换卷，也不代替上述步骤。

## 原授权与历史卷

backup.read 和备份中每个历史源卷 UUID 的 volume.read 都是必要权限。后续升级已经
发布新 UUID 时，备份仍按其原历史 UUID 检查。旧卷可以是墓碑且没有实际分配，
但必须仍有可核对的原 Owner；不能用当前部署卷权限代替历史选择。

登记绑定该次实际凭证和主体，工作器及终态重放都检查原授权来源与当前凭证交集。
同一账号的新会话不能替换原凭证。后续新授权不能扩大原 UUID
选择或复活已撤销来源。备份过期会阻止新的迁移读写；读取原操作的终态仍须通过
原权限校验，但不要求备份继续可用于新工作。

## 内部布局与当前验证

追加的 Schema 13 只给 volume_schema_jobs 增加有界 backup_registration，不修改
迁移 1–12。非 bootstrap 任务必须带备份登记，并绑定原 backup/deployment UUID、
插件/发布者及动作对应的备份格式；缺少 JSON 字段不能借 SQL UNKNOWN 绕过约束。
bootstrap 不携带备份登记。登记最多 4 MiB，完整备份清单及安装快照分别最多 1 MiB。

显式数据库升级目标随该开发分支变为 13。升级前须按既有停机、备份核实和未完成
任务检查流程操作；旧二进制及旧原生快照不能被误认为新布局兼容。

本地 PostgreSQL 用例验证不完整、非 off_host、缺失备份拒绝，历史墓碑读取权限，
完整原 UUID 选择，原凭证/来源撤销与新授权不能接管。它们只验证元数据和权限，
没有预置实际远端可用备份。真实对象完整性、冻结克隆比对和新目录恢复的底层
用例仍属于 storage::migration_backup；正式 AWS/异机灾备与完整监督器验收尚未完成。
